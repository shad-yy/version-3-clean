## Persona 5 — CEO

### Where the moat actually is
ESPN, BBC Sport, FlashScore, SofaScore and LiveScore all beat this site on data depth, latency and brand. Competing on "live scores" head-on is unwinnable. The defensible position visible in this codebase is the one thing those five do *badly*: **"which channel, in which country, at what local time, for this specific fixture."** `/watch/*` already does this for UK broadcasters. Nobody owns the global, per-fixture, per-territory broadcast-rights answer — and it is exactly the query shape that AI answer engines are being asked and cannot currently resolve from a single authoritative source.

But that moat is unreachable while the same pages sell subscriptions, because the broadcast-guide claim ("here is where to legally watch") is contradicted by the commercial layer on the same URL.

### 🔴 CRITICAL

**C-01 · The commercial funnel is the single largest ranking and monetisation risk.** A domain that publishes *"Best IPTV for Premier League"*, *"Is IPTV Legal in the UK?"* and *"How to Watch Premier League on Firestick Without Sky Sports"* alongside a WhatsApp order desk is not going to pass AdSense review, will not be cited by answer engines as an authority, and will not be linked to by any journalist or broadcaster. Every other item in this report is downstream of this one.

**C-02 · Live commercial API endpoints remain on the main domain.** See B-01 — `/api/orders` and `/api/subscribe` both return `405` to GET (route exists, POST accepted).

### 🟡 HIGH

**C-03 · Zero author attribution anywhere.** No author bios, no bylines, no editorial policy, no named humans. Google's 2026 core updates have consistently favoured "brands, official sites, and data-rich sources" over undifferentiated aggregators ([Search Engine Land — Google algorithm updates](https://searchengineland.com/library/platforms/google/google-algorithm-updates)). An anonymous site making unverifiable stat claims (U-03) is the profile those updates demote.

**C-04 · Seasonal window closing — 3 weeks to Premier League kickoff (21 Aug 2026).** The single highest-intent traffic moment of the year. Today the site is serving a finished 2025-26 table (U-01), hardcodes `s=2025-2026` in two live fetches (B-02), and its blog is 20/29 expired World Cup content (U-02).

### 💡 OPPORTUNITY

**C-05 · Own "where to watch X in Y country".** Extend `/watch/*` from UK-only to a `/watch/[competition]/[country]` matrix using real broadcaster data. This is programmatic SEO with genuine utility, it maps cleanly onto `BroadcastEvent` + `broadcastOfEvent` schema ([schema.org/BroadcastEvent](https://schema.org/BroadcastEvent)), and it is the exact question answer engines get asked.

**C-06 · Ship `SportsEvent` + `BroadcastEvent` markup on `/scores` and `/match/[id]`.** Highest-leverage technical SEO available — the data is already fetched and rendered; only the JSON-LD is missing. Prerequisite for Google's AI Mode sports entity cards.

**C-07 · Fix the freshness engine, then claim freshness.** `changeFrequency: 'daily'` on `/scores` is asserted but the API layer caches it for an hour (B-03). Correct the caching, then the freshness claim becomes true and defensible.

**C-08 · Convert the 20 expired World Cup pages into a permanent archive hub** (`/world-cup-2026/results`) with final scores and retained internal links, rather than leaving 20 pages promising "tonight" for July fixtures. Preserves accrued link equity instead of discarding it.

**C-09 · Publish a data-methodology page.** "Where our data comes from, how often it refreshes, what we do when a provider fails." Cheap to write, directly addresses the E-E-A-T gap in C-03, and is the kind of page that earns citations.

**C-10 · Upcoming calendar to target now:** Premier League 2026-27 kickoff 21 Aug 2026 (per the site's own copy); the summer transfer window; the Champions League league phase; and the F1 and UFC calendars already scaffolded in `/watch/formula-1` and `/ufc`.

## Layer 3 — Security

### 🔴 CRITICAL

**SEC-01 · Authenticated endpoints are marked publicly cacheable for 1 hour.**
```
$ curl -D - http://localhost:3000/api/auth/admin/status
Cache-Control: public, max-age=3600, stale-while-revalidate=86400
access-control-allow-origin: *
```
`next.config.mjs:174-180` applies this to `source: '/api/(.*)'` — **every** API route, including `/api/auth/admin/status`, `/api/auth/admin/extend`, `/api/admin/health`, `/api/admin/metrics`. `public` explicitly authorises shared caches (Vercel's edge CDN, any intermediary) to store and replay the response to other users. An admin's authenticated status response can be served from cache to an unauthenticated visitor for up to an hour, with `stale-while-revalidate` extending that to 24. Auth-bearing responses must be `private, no-store`.

**SEC-02 · The Upstash rate limiter guards the wrong path — the admin login endpoint is unprotected in production.**
`middleware.ts:103` gates on `pathname.startsWith('/api/admin/')`. The admin **login** route is `app/api/auth/admin/route.ts` → **`/api/auth/admin`**, which does *not* match that prefix. `/api/admin/*` is only health and metrics.
So `AUDIT-PROGRESS.md` C-04 ("Replace in-memory rate limiter with `@upstash/ratelimit`", marked `[x]`) protects health endpoints while leaving login on the in-process `globalThis.__adminRateLimit` Map (`app/api/auth/admin/route.ts:30-48`). On Vercel that Map is per-instance and per-cold-start, so the effective limit across a scaled deployment is *n* × 10 attempts per 5 minutes, resetting on every new lambda. Distributed brute force is not meaningfully constrained.

**SEC-03 · `bcrypt.compare()` runs before rate limiting and before input validation.**
`app/api/auth/admin/route.ts`: `const { password } = await request.json()` (line 22) → `bcrypt.compare(password, ADMIN_PASSWORD_HASH)` (line 28) → **then** the rate-limit block (lines 30-48). Two consequences:
1. Every request performs a full bcrypt hash *before* any throttle applies — `bcryptjs` is pure JS and single-threaded, so unauthenticated requests can saturate the event loop (CPU DoS).
2. `password` is never validated. A non-string or absent value reaches `bcrypt.compare` and throws into the catch, returning 500 instead of 400.
This is `AUDIT-PROGRESS.md` M-01, still open, and is more severe than its "MINOR" classification implies.

### 🟡 HIGH

**SEC-04 · CSP permits `unsafe-inline` and `unsafe-eval`.**
`next.config.mjs:161` — `script-src 'self' 'unsafe-inline' 'unsafe-eval' …`. Both [OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Content_Security_Policy_Cheat_Sheet.html) and [MDN](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy) state that a CSP allowing `unsafe-inline` on `script-src` provides essentially no XSS mitigation. The documented remedy is a per-response nonce ([Next.js CSP guide](https://nextjs.org/docs/app/guides/content-security-policy)), generated in `middleware.ts`. Note `img-src` also allows bare `http:`, permitting mixed content.

**SEC-05 · Five HIGH-severity dependency advisories** (`npm audit`: `{"high":5,"critical":0,"total":5}`) — see Layer 8.

### ✅ Verified correct
- HSTS `max-age=63072000; includeSubDomains; preload`, `X-Frame-Options: SAMEORIGIN`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` all present (`next.config.mjs:133-156`).
